# ABIES Current Backend — API Inventory (for the mobile build)

This is Phase 0 discovery for the mobile apps (brief: "ABIES Mobile — Enterprise Android + iOS").
Generated by walking every `route.ts` under `apps/platform-api/src/app/api/v1` (244 routes, 2026-10-07)
and reading the request/auth helpers each one calls. No hand-written endpoint is invented here; this
is what exists today.

## 1. Stack (as it exists, not assumed)

- **Backend**: Next.js 16 route handlers (`apps/platform-api`), one app per surface -- `platform-api`
  (patient + partner + admin APIs, `/api/v1/*` and the internal `/db/v1/*`), `client-web` (patient
  website), `management-web` (staff "ops" console), `partner-web`. All four are separate Next.js apps
  in one Turborepo, sharing the `@abies/domain` package (Prisma client, services, zod schemas).
- **Database**: PostgreSQL 16 via Prisma. One schema, one database -- `packages/domain/prisma/schema.prisma`.
  Mobile must not get its own database or duplicate a model; it calls the same `/api/v1/*` surface
  the website calls.
- **No OpenAPI/Swagger spec exists.** Request/response shapes are defined by zod schemas per module
  (`modules/<domain>/<domain>.schemas.ts`) and read directly from the route handler source. This is a
  gap -- see API-GAP-ANALYSIS.md 1.
- **Auth today is cookie-session, not a bearer token** (details in 3 below). This is the single most
  consequential fact for the mobile architecture -- see API-GAP-ANALYSIS.md 2 and SECURITY-DESIGN.md 2.

## 2. API surface: 244 routes under `/api/v1`, grouped by domain

"Auth" column: `session` = requires a valid session (cookie); `role-check` = also checks the caller's
role/department; `mfa` = step additionally requires a verified admin MFA code; `origin-check` = compares
the `Origin` header against `APP_BASE_URL` (CSRF-style check used by the CRM proxy routes, which forward
to the internal `db-service` with the caller's session token); `PUBLIC` = no session required at all.

There is a second, internal API surface at `/db/v1/*` (21 routes) used by `platform-api`'s own CRM proxy
and by `management-web` server-side. It authenticates callers by Kubernetes `TokenReview`, not by end-user
session, and is not something a mobile client calls directly -- it is mentioned here only so it is not
mistaken for a mobile-facing surface.

## 3. Authentication model

- **Identity**: `User` (id, `mobile` unique, `email` unique nullable, `name`, `role`, `status`,
  `mfaEnabled`). One user table for every role -- patients, doctors, labs, pharmacies, Panchakarma
  centres, and staff. No separate "customer" table.
- **Sign-in is OTP-only.** There is no password field on `User` today (a password option was recently
  approved for the web Contact/Login brief but is not yet built as of this writing).
  - `POST /api/v1/auth/otp/request` -- body `{ mobile }` or `{ email }`, plus `role`. Creates an
    `OtpChallenge` keyed on the account's mobile number, cooldown-limited (`OTP_COOLDOWN_SECONDS`),
    rate-limited by IP in `proxy.ts`.
  - **Delivery gap for a mobile app**: OTP delivery today only ever goes out on the EMAIL channel
    (`OTP_DELIVERY_CHANNEL=email`), and only if the account already has an email on file (or the caller
    signed in with an email in the first place). There is no SMS channel (removed platform-wide) and
    WhatsApp is off pending template approval. A brand-new user who registers with only a mobile number
    and no email cannot receive an OTP at all outside of the dev-mode bypass. This is a hard blocker for
    a "sign up with your phone number" mobile flow -- flagged in API-GAP-ANALYSIS.md 3, not something
    mobile code can work around.
  - `POST /api/v1/auth/otp/verify` -- body `{ requestId, code }`. On success, sets the session cookie
    and returns the user.
  - `POST /api/v1/auth/mfa/verify`, `GET /api/v1/auth/me`, `POST /api/v1/auth/logout`.
- **Session**: `Session` row plus an HttpOnly cookie named `abies_session` (`SESSION_COOKIE_NAME`,
  `packages/domain/src/server/session.ts`). `SESSION_TTL_DAYS=7`, sliding expiry -- `requireSession()`
  rotates the token and the route handler re-sets the cookie when a rotation is due. There is no
  bearer-token / `Authorization` header path for end-user auth anywhere in `/api/v1/*`.
  `requireSession()` (`packages/domain/src/server/rbac.ts`) reads `cookies()` directly -- a Next.js
  server API, not a generic header reader. (The `x-abies-session` caller-token mechanism that exists
  is specific to `db-service`'s internal Kubernetes-caller auth, not end-user mobile auth -- it should
  not be reused for mobile.)
- **RBAC**: `UserRole` enum -- `PATIENT, DOCTOR, ADMIN, LAB, PHARMACY, PANCHAKARMA_CENTRE,
  CUSTOMER_SUPPORT, TECH_SUPPORT, SALES, CARE_COORDINATOR, CRM_ADMIN, SALES_MANAGER, MARKETING, AUDITOR`.
  The mobile patient app only ever authenticates as `PATIENT`. Role/scope checks happen in the route
  handler or service layer (the "role-check" column above), never trust a client-side role claim.

## 4. Domain models relevant to mobile (Phases 4-9), already implemented

Appointments, Panchakarma (centres/therapies/therapists/bookings/sessions), Diagnostics (labs/tests/
packages/orders/reports), Pharmacy (medicines/orders/cart/prescriptions), Payments (Razorpay, webhook-
verified server-side), Refunds, Reviews, Support tickets, Consent (`ConsentArtifact`/`ConsentRecord`),
Audit (`AuditEvent`), Notifications (`Notification` row per channel attempt), Contact enquiries (just
added, guest-only). Full field-level detail is in `packages/domain/prisma/schema.prisma`; this doc does
not restate the schema, only which routes expose which model.

## 5. Notification channels (mobile relevance)

Email (Mailer91 SMTP, sender identities currently PENDING verification -- nothing sends yet) and
WhatsApp (off, `WHATSAPP_ENABLED=false`, pending template approval). No push-notification channel
exists -- there is no device-token model, no FCM/APNs integration, and no working `PUSH` sender (the
`NotificationChannel.PUSH` enum value exists but `notify()` records it as a permanent failure, "Push
notifications are not implemented yet", today). This is the main net-new backend work mobile needs --
see API-GAP-ANALYSIS.md 4.

## 6. Platform / deployment (what mobile CI plugs into, and what it must not touch)

RKE2 cluster; GitOps via ArgoCD (app `abies-dev`, repo `abies-gitops`, Kustomize overlays per
environment -- only `environments/dev` exists today, no UAT/prod overlay yet); builds via Tekton
(Pipelines + Triggers, Gitea webhook) pushing images to Harbor and bumping digest pins in the GitOps
repo; Envoy Gateway (Gateway API `HTTPRoute`s) fronting `dev.abies.in`, routing `/api*` to `platform-api`
and everything else to `client-web`/`management-web`/`partner-web` by path. None of this hosts mobile
binaries -- Kubernetes only ever hosts the backend. Mobile CI (Phase 11) is a separate pipeline that
produces `.apk`/`.aab`/`.ipa` artifacts; see IMPLEMENTATION-PLAN.md 11.

## 7. Environments that actually exist today

Only one: dev -- `https://dev.abies.in`, backed by the `abies-dev` ArgoCD app. There is no `uat` or
`prod` Kustomize overlay or DNS name in the GitOps repo yet. The brief's example hostnames
(`api-dev`/`api-uat`/`api.abies.in`) are illustrative, not real -- MOBILE-ARCHITECTURE.md 3 proposes
real values, flagged as provisional until a UAT/prod environment exists.
